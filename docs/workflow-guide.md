# 团队 Agent 敏捷研发 SOP 实战手册 (Workflow Guide)

传统的 AI 辅助编程往往是“开发者提一句话 $\to$ AI 盲目堆写几百行代码 $\to$ 开发者花费数小时排查 Bug 和坏味道”。

**`team-agent-standards`** 提倡一种**严谨、确定性、高交付质量**的敏捷工程全流程 SOP

---

## 阶段 1：方案深挖与对齐（Alignment）

- **痛点**：人类头脑中的很多边界条件、失败处理、架构依赖没有完全想透，直接让 AI 编码会导致反复返工。
- **操作**：
  在输入框中向 Agent 描述你的粗略想法，并在末尾输入：
  > “我想在评测平台中增加一个多模型对比功能，支持多轮对话打分。 /grill-me”
- **Agent 动作**：
  Agent 会化身苛刻的架构评审官，像剥洋葱一样，每次抛出关键决策问询（支持哪些模型？评分是单向还是双向？失败重试机制如何？存储用关系库还是 NoSQL？），直到所有设计决策彻底收敛。

---

## 阶段 2：输出规格说明书（Spec）

- **痛点**：口头聊完后共识容易遗忘，没有留痕文档。
- **操作**：
  访谈结束后，直接对 Agent 输入：
  > “整理为工程设计规格文档。 /to-spec”
- **Agent 动作**：
  Agent 将刚刚对话中达成共识的所有决策点、数据结构、流程图、异常边界梳理为一份结构严密的 Markdown 规格说明书。

---

## 3. 阶段 3：原子任务切片（Tickets）

- **痛点**：一次性让 AI 编写过大的功能模块，极易出现幻觉、Token 耗尽、上下文遗忘。
- **操作**：
  > “根据此 Spec 拆解开发任务。 /to-tickets”
- **Agent 动作**：
  将大型需求分解为 3~5 个小步快跑的原子任务（如 Ticket 1: 数据模型迁移；Ticket 2: API 接口与鉴权；Ticket 3: 前端交互面板），每个工单均带有前置阻塞依赖声明。

---

## 4. 阶段 4：测试驱动编码（TDD）

- **痛点**：AI 生成代码后手工测试成本高，极易引入隐蔽 Bug。
- **操作**：
  > “开始执行 Ticket 1，使用 TDD 模式开发。 /tdd”
- **Agent 动作**：
  严格遵守**红-绿-重构（Red-Green-Refactor）**流程：
  1. 先编写针对该功能的单元测试用例，运行并确认测试处于失败状态（Red）；
  2. 编写满足测试通过的最小代码实现，运行并确认测试通过（Green）；
  3. 对代码进行抽象清理，确保不破坏已有用例（Refactor）。

---

## 5. 阶段 5：双轴代码审查（Code Review）

- **痛点**：AI 生成的代码可能违背团队红线（如硬编码秘钥、函数超长、命名混乱）。
- **操作**：
  在代码写完、准备提 PR 前输入：
  > “审查自上一提交以来的所有变更。 /code-review”
- **Agent 动作**：
  启动双审查机制：
  1. **Standards 轴**：逐行对照 `rules/common.md` 检查是否有安全漏洞、吞异常、超长函数或魔鬼数字；
  2. **Spec 轴**：对照最初的 Spec 检查是否遗漏了任何边界需求。
  输出审查报告并给出针对性的修改建议。

---

## 6. 阶段 6：规范化提交与 PR（Ship）

- **操作**：
  要求 Agent 生成符合 Conventional Commits 规范的 Git 提交。
- **规范**：
  必须符合 `<type>(<scope>): <subject>`，如 `feat(eval): add multi-model comparison matrix`。
