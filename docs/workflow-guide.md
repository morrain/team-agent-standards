# 团队 Agent 敏捷研发 SOP 实战手册 (Workflow Guide)

在初期的 Agent 辅助研发中，开发者通常采用“向 Agent 丢一句话 $\to$ Agent 盲目堆写几百行代码 $\to$ 开发者花费数小时排查隐式 Bug、类型错误与坏味道”的工作方式。这种方式在简单脚本场景下尚可应付，但在复杂的工业级软件工程中，会导致频繁返工、上下文失真、脆弱测试以及严重的架构漂移。

**`team-agent-standards`** 提倡并固化了一套**高度结构化、强确定性、闭环交付**的敏捷工程全流程 SOP：

```mermaid
graph TD
    A[需求构想 / 架构重构] -->|/grill-me /grill-with-docs| B(方案深挖与共识对齐)
    B -->|/to-spec| C(沉淀设计规格说明书 Spec)
    C -->|/to-tickets| D(原子工单切片 Tickets)
    D -->|/tdd| E(测试驱动开发: 红-绿-重构)
    E -->|遇到异常| F{/diagnosing-bugs 科学排错}
    F -->|验证闭环| E
    E -->|/code-review| G(Standards + Spec 双轴审查)
    G -->|规范化提交| H[PR / 交付]
    D -.->|长上下文转交| I[/handoff 会话交接]
```

---

## 阶段 1：方案深挖与边界挖掘 (Alignment & ADR)

### 1.1 为什么需要此阶段？
人类大脑在构思新功能时，通常只能覆盖“主流程（Happy Path）”，大量边界条件、失败处理、权限鉴权、并发幂等与数据一致性并未彻底想透。如果直接让 Agent 编码，Agent 会根据其先验概率自行脑补假设，导致后期产生严重的架构返工。

### 1.2 操作指令
- **深挖边界漏洞**：输入粗略需求构思，末尾敲入 `/grill-me`：
  > “我想在评测平台中增加一个多模型对比功能，支持多模型并发调用与多轮对话打分。 /grill-me”
- **复杂选型沉淀 ADR**：涉及架构设计或库选型时，输入 `/grill-with-docs`：
  > “我们需要在项目中引入分布式缓存，评估 Redis 与本地内存缓存的选型。 /grill-with-docs”

### 1.3 Agent 标准动作与执行表现
- **化身严苛评审官**：Agent 不会立即给出代码，而是像“剥洋葱”一样，每次抛出 1~3 个关键设计决策追问：
  - *并发限制*：支持多少个模型并发？单次任务是否有全局超时与速率限制（Rate Limit）？
  - *重试与幂等*：某个模型调用超时或 504 时，是整体失败还是支持单模型独立重试？
  - *存储选型*：打分数据是存储在现有关系库还是独立的 NoSQL 中？数据模型如何设计？
- **沉淀 ADR 架构决策记录**：使用 `/grill-with-docs` 时，Agent 会在讨论的同时自动在项目 `docs/adr/` 目录下生成符合标准的架构决策记录（包含 Status、Context、Decision、Consequences）。

## 阶段 2：输出设计规格说明书 (Spec)

### 2.1 为什么需要此阶段？
访谈结束后，对话历史中充斥着大量的来回讨论与碎片化共识。如果不及时固化为结构化规格书，这些共识会在后续的长对话中被截断或遗忘。

### 2.2 操作指令
在访谈收敛后，直接向 Agent 指示：
> “根据刚才讨论达成的全部共识，整理为正式工程规格说明书。 /to-spec”

### 2.3 Agent 标准产出物
Agent 会生成一份结构严谨、自包含的 Markdown 规格说明书（通常保存在 `docs/specs/` 或当前任务上下文）：
1. **背景与业务目标 (Problem & Goals)**：清晰界定要做什么与不做系统范围之外的事（Non-Goals）；
2. **数据模型与契约 (Data Contracts)**：给出精确的 TypeScript Interface、JSON Schema 或 Protobuf 定义；
3. **系统时序与状态流转 (Sequence & State Diagrams)**：以 Mermaid 图表明确调用时序与状态机变化；
4. **异常边界与降级策略 (Edge Cases & Fallbacks)**：明确列出网络超时、参数缺失、鉴权失败的具体行为；
5. **验收标准清单 (Acceptance Criteria)**：可转化为自动化测试用例的具体断言项。

---

## 阶段 3：原子工单切片 (Tickets)

### 3.1 为什么需要此阶段？
一次性要求 Agent 编写数百上千行的大型功能模块，极易引发大模型的“上下文遗忘”和“大步跨越式幻觉”。将大型 Spec 拆解为垂直切片的微型任务，是保证 Agent 交付高确定性的关键。

### 3.2 操作指令
在 Spec 确认无误后，指示 Agent：
> “请对照此 Spec，将其拆解为原子任务卡片。 /to-tickets”

### 3.3 Agent 标准动作与产出
Agent 将大型需求分解为 3~5 个“小步快跑”的原子工单（Tickets），每个工单具备如下特性：
- **声明依赖关系**：例如 `Ticket 2 (依赖 Ticket 1)`；
- **单一职责与范围闭环**：每个工单只做一件独立可测试的事情（如 Ticket 1: 数据库表结构迁移与 DAO 层；Ticket 2: Service 核心计算与业务异常；Ticket 3: Controller API 路由与参数校验）；
- **Token 友好**：单个工单涉及的代码文件一般不超过 3 个，方便 Agent 集中注意力精确交付。

---

## 阶段 4：测试驱动实现 (TDD & Implementation)

### 4.1 为什么需要此阶段？
直接让 Agent 编写业务实现，极易出现“缺乏边界自测、代码逻辑看起来很对但一跑就崩”的问题。TDD（测试驱动开发）强迫 Agent 先写出可证伪的测试用例，将实现代码的正确性锚定在绿色的单元测试上。

### 4.2 操作指令
根据任务规模与交付诉求选择合适指令：
- **单任务 / 小特性闭环交付**（当前分支直接端到端构建、自测与提交）：
  > “开始执行 Ticket 1，端到端完成测试自测与审查。 /implement #1”
- **全套 Spec 多任务并发交付**（自动开辟集成分支、调度多子 Agent 并发构建）：
  > “严格对照此 Spec 与工单任务图并发交付完整特性。 /implement-spec”
- **单模块测试驱动编码**（微观红-绿切片开发）：
  > “开始为该函数编写测试驱动实现。 /tdd”


### 4.3 Agent 严格遵守的红-绿-重构纪律 (Red-Green-Refactor)
1. **Red（红）**：
   - 先编写针对该工单的核心业务单元测试用例；
   - **真实运行测试命令**（如 `npm test` 或 `pytest`），捕获预期的失败日志，确认测试确实处于失败状态；
2. **Green（绿）**：
   - 编写满足测试通过的**最小代码实现**（拒绝过度设计）；
   - **再次真实运行测试命令**，确保测试 100% 变绿；
3. **Refactor（重构）**：
   - 对代码进行结构抽象、消除重复、优化圈复杂度；
   - 每次微调后重新跑测，确保重构不破坏已有契约。

> [!CAUTION]
> 团队规则严禁“口头宣称测试通过”。Agent 必须在终端中真实执行命令，并在回复中附带实际执行的命令及输出日志凭据。

## 阶段 5：科学闭环排错 (Hypothesis-Driven Debugging)

### 5.1 为什么需要此阶段？
许多开发者与 Agent 在遇到报错时习惯“碰运气”：看到错误就随意改一行代码再试一次，这种“随机试错”不仅无法解决问题，还会引入大量垃圾代码与次生 Bug。

### 5.2 操作指令
当遇到复杂报错或测试失败时，输入：
> “排查此测试失败原因。 /diagnosing-bugs”

### 5.3 Agent 科学排错三部曲
1. **定位事实 (Gather Facts)**：完整阅读报错堆栈（Stack Trace）、错误日志、入参数据，确定失败发生的精确代码行；
2. **提出假设 (Formulate Hypothesis)**：结合代码上下文与架构逻辑，提出唯一且可证伪的根因假设（例如：“由于异步 Promise 未被 await，导致数据库连接提前释放，抛出连接池已关闭异常”）；
3. **靶向验证 (Targeted Verification)**：做最小化的定向代码修复，再次运行测试命令验证假设；如果假设失败，回滚改动并重新提出新假设，绝不留下试错残留。

---

## 阶段 6：双轴代码审查 (Code Review)

### 6.1 为什么需要此阶段？
Agent 在生成代码时可能在局部满足了功能需求，但违背了团队工程规范（如：函数过长、圈复杂度超标、缺少超时控制、未脱敏日志）。提 PR 前必须进行独立自审。

### 6.2 操作指令
在全部工单完成、准备提交前指示 Agent：
> “审查自上一提交以来的所有代码变更。 /code-review”

### 6.3 Agent 双轴并行审查机制
Agent 会启动两个视角的并行审查，并输出结构化审查报告：
1. **Standards 规范轴**：
   - 逐行对照团队核心规则（`rules/common.md`, `rules/testing.md` 等）；
   - 检查是否有硬编码敏感凭证、空的 `catch` 吞异常、函数超 50 行、圈复杂度超 10、脆弱的内部私有方法 Mock；
2. **Spec 需求轴**：
   - 对照最初生成的规格说明书（Spec）与工单；
   - 检查是否遗漏了任何边界分支、异常返回格式是否与契约完全一致。

---

## 阶段 7：长会话交接 (Session Handoff)

### 7.1 为什么需要此阶段？
当开发复杂特性时，会话历史可能积累了数万甚至数十万 Token，此时大模型注意力衰减、响应变慢。或者需要将工作转交给同事接手。

### 7.2 操作指令
在需要结束当前长会话前输入：
> “提炼当前任务进度，生成交接文档。 /handoff”

### 7.3 Agent 标准产出
Agent 会提炼并输出一份 Markdown 交接卡片：
- **已完成工作 (Completed Work)**：清晰列出已完成的 Ticket 及对应的测试用例；
- **进行中状态 (Current In-Progress)**：当前正在修改的具体文件、断点与未解决的关键疑点；
- **后续待办事项 (Next Steps)**：接手者或新会话启动后应立刻执行的下一条命令与工单。
在新会话中直接粘贴该交接卡片，即可零信息损耗无缝接力开发！
