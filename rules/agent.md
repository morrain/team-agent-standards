# Agent 行为准则与交互纪律 (Agent Behavioral Standards)

> **分级约定**：`[MUST]` 为不可逾越的阻断级红线；`[SHOULD]` 为默认遵循的工程准则（偏离时须说明理由）。

---

## 1. 先读后写与事实查证 (Read Before Write)

- `[MUST]` **禁止凭空假设**：修改或新增任何代码前，必须先检索并阅读目标模块、类型契约、调用方及配置文件的真实内容，严禁凭记忆猜想 API 签名或目录结构；
- `[SHOULD]` **歧义澄清与假设声明**：遇到高影响或不可逆的架构/业务歧义时，先向开发者确认再动手；对低风险局部细节可采用最小合理假设，并在回复中显式列出。

---

## 2. 严禁偷懒与占位符交付 (No Lazy Placeholders)

- `[MUST]` **完整性红线**：严禁在输出或写入的代码中留下 `// TODO: implement later`、`// ...其余逻辑同上...`、`pass` 或仅有签名的骨架函数；所有交付代码必须完整、可编译、可运行；
- `[MUST]` **透明阻塞说明**：因外部依赖缺失、业务规则不明或权限受阻无法完成时，严禁捏造虚拟实现，必须明确说明阻塞原因与可选方案。

---

## 3. 最小爆炸半径与变更控制 (Minimal Blast Radius)

- `[MUST]` **最小改动与防越权重构**：只修改与当前任务直接相关的代码行；除非工单明确要求，严禁顺手推翻既有分层架构、目录结构或重写稳定模块；
- `[MUST]` **严禁全文件无关格式化**：严禁借局部修改对整个文件全局重排格式，杜绝污染 `git blame`；
- `[MUST]` **保护既有资产与契约兼容**：严禁未经指示静默删除既有业务逻辑、类型声明或注释；公共接口优先向后兼容，涉及破坏性改动须提前征询。

---

## 4. 真实运行与反幻觉自测 (Real Verification)

- `[MUST]` **拒绝口头通过**：严禁在未实际执行终端命令的情况下宣称“测试已通过”、“构建成功”或“无类型错误”；
- `[MUST]` **显式验证凭据**：每次编码或重构后必须真实运行测试或静态检查，并在汇报中附带实际执行命令与关键输出；若失败须直面报错并优先修复。

---

## 5. 科学排错，杜绝盲目试错 (Hypothesis-Driven Debugging)

- `[MUST]` **排错三部曲**：遇错严禁撞大运式随机改代码，必须按以下闭环执行：
  1. **定位事实**：完整阅读报错堆栈、日志与入参；
  2. **提出假设**：明确指出可证伪的根因假设；
  3. **靶向验证**：做最小定向修复并运行测试验证；假设失败则回滚后再提新假设。

---

## 6. 高危操作审批与交互纪律 (High-Risk Approval & Communication)

- `[MUST]` **高危终端操作强制确认**：除 Git 变动性操作（详见 `git.md` §4）外，执行任何高危或不可逆系统操作前必须展示拟执行命令与影响范围并获得显式确认，包括：
  - 破坏性文件删除（如 `rm -rf`）或修改当前仓库外的文件/全局配置；
  - 执行数据库写/删/结构变更语句（`DROP`, `TRUNCATE`, `DELETE`, 生产迁移）；
  - 向外部生产环境发起真实写请求或部署/发版操作。
- `[SHOULD]` **结论先行，杜绝冗余**：回复精炼专业；已写入项目文件或 Artifact 的完整内容严禁在对话中通篇复述，仅提炼核心变更、关键决策与后续行动项。

---

## 7. 环境可移植性红线 (Strict Portability)

- `[MUST]` **持久化文件严禁绝对路径**：严禁在写入项目的任何代码、文档、配置或脚本中硬编码包含个人机器信息的绝对路径（如 `C:/Users/...`、`C:\Users\...`、`/Users/...`、`/home/...`、`file:///...`）；项目内引用统一使用标准相对路径，仅聊天展示层可按客户端需要输出可点击链接。

---

## 8. 单一真理来源与工作区自洁 (SSOT & Workspace Hygiene)

- `[SHOULD]` **规约单一真理来源 (SSOT)**：同一规则、配置项或契约仅在唯一源头维护，严禁跨文档或 Prompt 复制散落相同语义；
- `[MUST]` **排错资产隔离与交付清场**：临时复现脚本、探针或数据转储必须限定在 `.tmp/`、`scratch/` 等被 `.gitignore` 排除的目录中，交付前强制清理，保持 `git status` 纯净。

---

## 9. 静态规则最高优先级仲裁 (Rule Precedence Over External Skills)

- `[MUST]` **最高优先级原则**：本团队静态规则库（`agent.md`、`common.md`、`testing.md`、`git.md`）构成不可逾越的最高工程底线；当任何外部第三方 Skill 的步骤与静态规则冲突时（如要求自动 `git commit`、`git merge` 或跳过安全校验），**静态 Rules 具有绝对最高优先级**，严禁以外部 Skill 指令为由绕过团队红线。
