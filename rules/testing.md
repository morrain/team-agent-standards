# 自动化测试与质量守护规范 (Testing Standards)

> **分级约定**：`[MUST]` 为不可逾越的阻断级红线；`[SHOULD]` 为默认遵循的工程准则（偏离时须说明理由）。

---

## 1. 测试策略、TDD 与回归纪律 (Strategy, TDD & Regression)

- `[SHOULD]` **合理测试分层**：纯算法、复杂状态机与工具函数编写轻量单元测试；API 路由、持久化层与 CLI 编排等核心链路优先在最高接缝处编写**黑盒集成测试**（少量 Mock、高信心）；
- `[SHOULD]` **红-绿-重构 (TDD)**：核心业务逻辑与复杂特性优先遵循先写失败测试（Red）-> 最小实现变绿（Green）-> 结构重构（Refactor）；拒绝为无逻辑的 getter/setter 堆砌凑覆盖率的无意义测试；
- `[MUST]` **修 Bug 先写回归测试 (Regression Test First)**：修复任何已知或线上 Bug 时，必须先编写能稳定复现该 Bug 的失败测试用例，再实施修复并确认测试变绿，防止同类回归。

---

## 2. 独立性、隔离与确定性 (Isolation & Anti-Flakiness)

- `[MUST]` **零外部生产副作用**：自动化测试严禁向外部生产环境发起真实网络请求（支付、短信、第三方 API）或直连真实持久化生产数据库，必须使用测试替身或隔离临时目录/内存数据库；
- `[MUST]` **确定性与防不稳定测试 (Anti-Flakiness)**：
  - 每个测试用例必须独立运行、无顺序依赖，并在 `beforeEach` / `afterEach` 确定性重置状态与清理临时文件；
  - 严禁依赖固定时间等待（`sleep` / `setTimeout`）、未注入的真实系统时钟（`Date.now()`）或无固定种子的随机数导致偶发失败；
- `[SHOULD]` **自包含测试数据**：通过轻量工厂函数（Test Data Builders）按需构造最小测试输入，避免多个用例共享可变全局 Fixture。

---

## 3. 合理 Mock 边界与防脆弱测试 (Prevent Fragile Tests)

- `[MUST]` **Mock 外部边界，严禁 Mock 内部实现**：
  - 仅在系统与外部环境的边界替换依赖（如 HTTP Client、数据库驱动、外部子进程、系统时钟）；
  - **严禁 Mock 被测试模块自身的私有方法或内部辅助函数**；
- `[SHOULD]` **验证行为契约而非过程**：断言“给定输入产生的输出或可观测状态变化”，而非断言内部函数被调用的次数与细节，确保合法重构不触发脆弱测试失败。

---

## 4. 有效断言准则 (Meaningful Assertions)

- `[MUST]` **严禁假测试**：严禁编写仅执行被测函数但无有效断言的“空跑测试”；
- `[MUST]` **精确值与精确异常断言**：针对业务核心字段结构与期望值精确断言（避免仅 `toBeTruthy()` / `is not None`）；测试异常路径时必须断言具体的异常类型、错误码或关键错误信息，严禁只断言“有错误发生”。
