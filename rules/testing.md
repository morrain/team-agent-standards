# 自动化测试与质量守护规范 (Testing Standards)

本文件定义团队所有项目自动化测试的设计基准、Mock 规范与测试执行纪律。所有 Agent 在编写新功能、重构或修复 Bug 时必须严格遵守。

---

## 1. 测试驱动与覆盖基线 (TDD & Coverage)

- **红-绿-重构纪律**：编写新业务特性或修复复杂 Bug 时，优先遵循 TDD（测试驱动开发）：
  1. 先编写失败的测试用例（Red）；
  2. 编写满足测试通过的最小代码实现（Green）；
  3. 进行重构并确保测试持续通过（Refactor）。
- **核心逻辑必测**：核心业务状态机、核心计算、权限鉴权逻辑以及非空/异常边界分支必须有单元测试覆盖；
- **有效覆盖优先**：拒绝为了表面测试覆盖率而给无逻辑的 getter/setter 或纯配置类堆砌无意义测试。

---

## 2. 测试独立性与环境隔离 (Isolation & Zero Side-Effects)

- **无顺序依赖**：每个测试用例必须能够独立运行并产出确定结果，严禁测试用例间存在执行先后依赖；
- **零外部副作用**：
  - 单元测试严禁向外部生产环境发起真实网络请求（如支付、短信、第三方 API）；
  - 严禁直连真实持久化生产数据库；
  - 必须使用 Mock、Stub 或内存临时数据库（如 SQLite in-memory）；
- **生命周期状态清理**：在 `beforeEach` / `afterEach`（或 `setUp` / `tearDown`）钩子中，必须确定性重置全局缓存、Mock 状态并清理测试生成的临时文件。

---

## 3. 合理 Mock 原则与防脆弱测试 (Prevent Fragile Tests)

- **Mock 外部边界，而非内部实现**：
  - 只在系统与外部环境的边界进行 Mock（如 HTTP Client、数据库驱动、系统时钟、外部消息队列）；
  - **严禁 Mock 被测试模块自身的内部私有方法或内部实现细节**。
- **验证行为契约，而非代码实现过程**：
  - 测试应当断言“给定输入产生什么输出或可观测状态变化”，而不是断言“内部函数被执行了多少次”；
  - 脆弱测试（Fragile Tests）会导致合法的内部代码重构频繁触发测试失败，严重破坏研发效能。

---

## 4. 有效断言准则 (Meaningful Assertions)

- **严禁假测试**：严禁编写仅调用被测函数但缺乏断言的“空跑测试”；
- **精确断言**：避免使用宽泛模糊的断言（如仅 `expect(res).toBeTruthy()` 或 `assert res is not None`），必须针对关键业务字段的结构与期望值进行精确断言；
- **精确异常断言**：测试异常边界时，必须断言抛出的特定异常类型或错误码，严禁只断言“有错误发生”。
